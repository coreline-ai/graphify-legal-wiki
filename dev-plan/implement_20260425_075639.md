## 개발 목적
`data/legalize-kr/graphify-out/graph.json`를 최종 사용자가 쉽게 질의하고 검증할 수 있도록, 법령 그래프 기반 챗봇형 GUI를 개발한다. 사용자는 원본 JSON/Markdown을 직접 열지 않고도 질문, 근거 확인, 관련 subgraph 탐색, 산출물 상태 검증을 한 화면에서 수행할 수 있어야 한다.

## 개발 범위
- 1차 기준 그래프: `data/legalize-kr/graphify-out/graph.json`.
- 사용자 확인 문서: `data/legalize-kr/graphify-out/VERIFY.md`.
- backend API: 그래프 상태, 질의, 노드 설명, 경로 탐색, 관련 subgraph 반환.
- frontend GUI: 챗봇형 질의 UI, 근거 패널, graph 상태 패널, wiki/report 링크, 추천 질문.
- 디자인 기준 문서: `docs/design/obsidian-inspired-graph-chat-guide.md`와 `docs/design/obsidian-inspired-tokens.css`를 GUI 구현의 1차 스타일 소스로 사용한다.
- Obsidian-inspired workspace 패턴은 정보 구조, 작업 밀도, pane/ribbon/tab/graph UX만 참고하고 Obsidian 브랜드 자산은 사용하지 않는다.
- 질문 결과 기반 `3D subgraph panel`: 챗봇 답변에 연결된 관련 node/edge만 3D로 렌더링한다.
- `community-level overview 3D`: 전체 그래프를 12개 community 단위로 축약한 3D overview를 제공한다.
- 별도 메뉴: 전체 `9,001` nodes / `176,128` edges를 실험적으로 렌더링하는 `Full 3D Graph` view.
- 1차 구현 방식 권장안: `FastAPI` backend + `React/Vite` frontend.
- graphify 본체 기능은 재사용하고, 법률 해석/자문 엔진을 새로 만들지 않는다.

## 문서 기반 제약 사항
- graphify 산출물은 `graphify-out/` 아래의 `graph.json`, `GRAPH_REPORT.md`, `wiki/`, `graph.html`를 기준으로 한다.
- graphify community detection은 embedding/vector DB가 아니라 graph topology 기반이다.
- `graph.json`은 약 86MiB, `9,001` nodes / `176,128` edges 규모라 frontend에 전체를 즉시 로드하지 않는다.
- 기본 분석 UX는 `질문 결과 기반 3D subgraph`와 `community-level overview 3D`를 우선한다.
- 전체 3D 그래프는 기본 진입 화면에서 자동 로드하지 않고, 별도 메뉴 클릭 시 lazy-load한다.
- 전체 3D 그래프는 시각 확인용/탐색용 실험 기능으로 취급한다. 성능 저하 가능성을 UI에 명시하고, edge 표시 토글/검색/focus/정지 기능을 제공한다.
- 현재 `graphify query`는 고차수 허브 중심으로 넓게 퍼질 수 있으므로 GUI에서는 결과를 source/evidence 중심으로 정제해서 보여준다.
- 이번 기준 그래프는 `deterministic_legal_reference` 방식이며 LLM semantic extraction 결과가 아니다.
- 신규 GUI 컴포넌트는 `docs/design/obsidian-inspired-tokens.css`의 `--lg-*` design token을 우선 사용하고, 색상/spacing/radius 하드코딩을 피한다.
- Obsidian의 로고, 앱 아이콘, 제품명 lockup, 공식 브랜드 에셋은 사용하지 않는다. UI는 “Obsidian-inspired” 수준의 구조적 참고로 제한한다.
- 3D graph 계열 UI는 디자인 가이드의 color/size/edge mapping을 따른다: community=color, degree=size, confidence/weight=edge opacity/thickness.
- backend는 기본적으로 local-only 개발 도구로 시작한다. 기본 host는 `127.0.0.1`이고 CORS는 frontend dev origin으로 제한한다.
- source file 열람 기능은 `data/legalize-kr` 및 `data/legalize-kr/graphify-out` 하위 read-only 파일로 제한한다. 임의 경로 read, path traversal, symlink escape는 금지한다.
- API 응답은 UI가 필요한 slim DTO만 반환한다. `graph.json` 원본 구조를 그대로 외부 API로 노출하지 않는다.
- 모든 대용량 payload는 limit, timeout, payload byte budget, lazy-load/fallback 전략을 명시해야 한다.

### 병합 순서

1. **A Docs/Design foundation**을 먼저 병합한다. 이후 워커는 이 문서와 `apps/legal-graph-chat/README.md`를 contract source of truth로 본다.
2. **B Backend API/Query**가 OpenAPI/error shape/payload limit을 확정해 병합한다. API 필드 변경 시 README와 contract snapshot을 같은 PR에서 갱신한다.
3. **C Frontend MVP**는 B의 mock 또는 실제 endpoint contract에 맞춰 병합한다. backend 내부 구현을 직접 import하지 않는다.
4. **D Graph/3D panels**는 `/subgraph/3d`, `/communities/3d`, `/graph/full-3d` contract가 안정된 뒤 병합한다. 전체 3D는 기본 화면에서 network request를 발생시키면 안 된다.
5. **E QA/Integration**은 마지막에 backend unit, API contract, frontend smoke, 3D lazy-load/performance 결과를 묶어 병합한다.

### 충돌 방지 규칙

- 각 워커는 자신의 소유 경로 밖 변경을 되돌리지 않는다.
- `docs/design/obsidian-inspired-tokens.css`의 token rename은 frontend 구현 후 breaking change가 되므로, rename보다 alias 추가를 우선한다.
- API endpoint/DTO/error shape 변경은 README와 contract test를 함께 변경하지 않으면 merge-ready로 보지 않는다.
- `data/legalize-kr/graphify-out/graph.json` 원본은 read-only input이다. GUI 구현 편의를 위해 원본 파일을 수정하지 않는다.
- `Full 3D Graph`는 항상 opt-in + lazy-load + warning modal + fallback state를 요구한다.

## 전문가 리뷰 결과

### 종합 판단
- Engineering completeness: `7/10 → 8.5/10`. 기존 계획은 목표와 Phase 구성이 좋지만, API contract, 보안 경계, 테스트 fixture, query ranking, 성능 budget이 부족했다.
- Design completeness: `8/10 → 9/10`. 디자인 문서와 token은 충분하지만, 실제 구현 Phase에 responsive/empty/error/keyboard 상태를 더 명시해야 한다.
- 핵심 권장: “챗봇 + evidence + 제한된 3D subgraph”를 기본 성공 경로로 두고, `Full 3D Graph`는 opt-in 실험 view로 유지한다.

### What already exists
- `graphify/serve.py`에는 graph loading, node scoring, node lookup, neighbor, community, shortest path, graph stats 로직이 이미 있다.
- `graphify/security.py`에는 path/label/url validation helper가 있다.
- `tests/`는 module별 unit test 구조가 이미 잡혀 있다.
- 결론: FastAPI backend에서 동일 로직을 다시 만들지 말고, `serve.py`의 순수 query helper를 재사용 가능 모듈로 분리하거나 얇게 감싸야 한다.

### 추가해야 하는 핵심 보강 사항
- API DTO/schema를 먼저 고정한다. Pydantic response model과 frontend TypeScript type이 어긋나면 Phase 3 이후 디버깅 비용이 커진다.
- source viewer/file link는 보안 경계를 먼저 정한다. 웹 UI가 로컬 파일 경로를 보여주더라도 backend가 임의 파일을 읽으면 안 된다.
- query ranking은 hub dampening이 필요하다. `민법` 같은 고차수 node가 모든 질문을 삼키지 않도록 degree-normalized score, seed limit, stop hub 정책을 둔다.
- 3D payload에는 성능 budget이 필요하다. node/edge count limit뿐 아니라 byte size, timeout, progressive loading, edge default mode를 정한다.
- QA는 backend unit test, API contract snapshot, frontend interaction test, 3D lazy-load/performance smoke를 분리한다.

### NOT in scope
- LLM 기반 법률 답변 생성: 별도 provider/API key/비용/법률 문구 검토가 필요하므로 이번 MVP에서는 제외한다.
- 판례 corpus 통합: graph schema와 ranking 기준이 달라질 수 있어 별도 계획으로 분리한다.
- 인증/배포/멀티사용자 권한: local-first 검증 UI 완성 후 별도 계획으로 분리한다.
- 전체 graph 실시간 force simulation 튜닝 고도화: Full 3D view는 실험 기능으로 제공하고, 분석 UX는 subgraph/overview 중심으로 유지한다.
